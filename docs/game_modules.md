# Игровой модуль и hot reload

`game3` — отдельный CMake-проект. В Windows он собирает `game3.dll`,
в Linux — `game3.so`, в macOS — `game3.dylib`. Движок не компилирует игровые
исходники и не содержит игровой логики. Для разработки используется SDK
из каталога сборки движка: заголовки, компоненты движка и **та же shared Flecs**.
SDK пока не является переносимым install-пакетом.

SDK также экспортирует `spdlog::spdlog` через `spdlog-targets.cmake`.
Игра подключает его в `src/CMakeLists.txt` после `add_library(game3 SHARED ...)`.
spdlog собирается как общая shared-библиотека движка и игры: её состояние
и thread-local cleanup не должны оставаться внутри выгружаемого игрового образа.

## Сборка и запуск

```sh
cmake -S /home/ev3ryy/src/ior_engine -B /home/ev3ryy/src/ior_engine/build -DCMAKE_BUILD_TYPE=Debug
cmake --build /home/ev3ryy/src/ior_engine/build --parallel

cmake -S /home/ev3ryy/src/game3 -B /home/ev3ryy/src/game3/build \
  -DCMAKE_BUILD_TYPE=Debug \
  -Dior_game_sdk_DIR=/home/ev3ryy/src/ior_engine/build/sdk/Debug
cmake --build /home/ev3ryy/src/game3/build --parallel

/home/ev3ryy/src/ior_engine/build/ior_engine --game /home/ev3ryy/src/game3/build/game3.so
```

При изменении игры достаточно повторить последнюю команду сборки `game3`.
Движок опрашивает файл каждые 250 мс и ждёт два одинаковых наблюдения размера
и времени изменения. Затем копирует библиотеку в отдельный приватный временный
каталог. Размер и время проверяются также после копирования. У каждого импорта
свой путь; сборка не перезаписывает исполняемый образ. Неудачная версия повторно
не загружается до следующего изменения файла. `game_library::reload()` позволяет
повторить загрузку вручную.

Для multi-config генераторов используется `--config Debug`, SDK остаётся
в `build/sdk/Debug`, а путь к библиотеке зависит от выбранной конфигурации.
В Windows Flecs/SDL DLL должны быть доступны загрузчику ОС. Дополнительные
зависимости игры должны разрешаться и из временного каталога.

## Владение Flecs

Движок создаёт единственный `flecs::world` и регистрирует `local_transform`
и `local_to_world`. Их ID передаются через `ior_game_host`: игра не вызывает
`world.component<ior_engine::local_transform>()` и не заводит копии этих типов.

Вся игровая часть принадлежит дереву `::Game`:

```text
Game                 # корень, которым владеет загрузчик
├── Update           # вызывает game3::update один раз за кадр
└── Logic            # world.import<game3::GameModule>()
    ├── Velocity     # компонент игры
    ├── Move         # запрос движения, которым пользуется update
    └── Player       # сущность игры
```

`GameModule` задаёт имя `::Game::Logic` через `world.module<GameModule>()`.
Пример движения использует C API Flecs и ID компонента движка. Игровой
`Velocity` регистрируется в этом дереве без отдельного C++ кэша типа.
Новые игровые системы, наблюдатели, компоненты, префабы и сущности также
должны создаваться под `::Game`. Для создания сущностей в runtime указывайте
родителя явно: scope конструктора модуля не действует во время кадров.

Выгрузка удаляет корень `::Game` через `destruct()`. Это также удаляет
вложенный импортированный модуль, системы, запросы, контексты и игровые
компоненты. **Библиотека остаётся загруженной до завершения удаления**, чтобы
Flecs мог вызвать её деструкторы и cleanup-функции. После этого освобождается
образ библиотеки и временный каталог. Игровая библиотека скрывает C++ символы;
GNU unique symbols отключены, чтобы ОС действительно могла её выгрузить.

Reload начинает игру заново: игровое состояние и ID игровых сущностей не
сохраняются. Компоненты движка сохраняют ID; сущности движка вне `::Game`
сохраняются. Внешние ссылки на игровые сущности, указатели на их компоненты,
функции и запросы после reload недействительны. Не храните их между reload.
Если игровой компонент использовался на сущности движка, при выгрузке этот
компонент также удалится с неё.

## Граница и ошибки

Единственная экспортируемая функция — `ior_game_query`. Она возвращает
версионированную таблицу `ior_game_api`. Перед заменой загрузчик проверяет
версию ABI, размер таблицы, версию Flecs, размеры/выравнивания компонентов
движка, адрес функции общей Flecs и наличие `init`, `update`, `quit`.

Функции игры находятся в `game3/src/game.h` и `game.cpp`:

- `init(host, &context)` импортирует модуль, создаёт компоненты и игрока,
  подготавливает запрос движения. Контекст выделяется внутри игровой DLL;
  данные `host` копируются, его указатель действителен только во время `init`.
- `update(context, delta_time)` вызывается ровно один раз за `world.progress()`
  через систему `::Game::Update`, на потоке мира с доступным для записи миром.
  Время шага берётся у Flecs. Пример выполняет запрос и перемещает сущности.
- `quit(context)` освобождает запрос и контекст внутри той же DLL. Загрузчик
  вызывает его до удаления `::Game` и до выгрузки DLL: при выходе, reload,
  явной выгрузке и после неудачного `init`. Он должен поддерживать `nullptr`
  и частично инициализированный контекст. На одну попытку `init` приходится
  один `quit`; при отклонении DLL до `init` lifecycle не запускается.

Движок продолжает быть единственным владельцем `world.progress()`; игра
не должна вызывать его повторно внутри `update`. ABI обновлён до версии 2,
поэтому старые библиотеки с единственным `attach` отклоняются.

Отсутствующий экспорт, несовместимая или повреждённая библиотека отклоняется
до удаления работающего модуля. Если `init` вернул `false`, вызывается `quit`, его частичное
дерево удаляется, и предыдущая ещё загруженная библиотека импортируется
повторно. Её игровое состояние также начинается заново. Если повторный импорт
тоже не удался, игровой модуль остаётся выгруженным, ошибка доступна через
`error()`. Изначальный неудачный `--game` завершает запуск с ошибкой.

Это защита жизненного цикла собственного доверенного C++ модуля. Нативный
код исполняется в процессе движка; загрузчик не изолирует аварии или
произвольные изменения памяти. Проверки ABI не заменяют согласованную сборку.
При изменении SDK, состава/семантики компонентов или параметров ABI нужно
повысить `ior_game_abi`, пересобрать оба проекта и перезапустить движок.

Правила модуля:

- Не выбрасывать исключения через ABI и Flecs callbacks. `init` перехватывает
  исключения внутри библиотеки и возвращает `false`.
- Не регистрировать игровые hooks на компонентах движка, `ecs_atfini`,
  `atexit`, глобальные callbacks, не хранить код игры в сущностях вне дерева.
- Не создавать фоновые потоки или внешние callbacks, переживающие модуль.
  Внешние ресурсы должны освобождаться при удалении дерева, пока DLL доступна.
- Вызывать загрузчик только на потоке мира между `world.progress()` и после
  завершения использующих игру задач. Вызовы с другого потока, из readonly
  мира или во время кадра отклоняются. Объект загрузчика уничтожается до мира;
  нарушение этого контракта в деструкторе приводит к `terminate`, а не к
  выгрузке всё ещё исполняемого кода.

## Проверка

```sh
cmake -S /home/ev3ryy/src/ior_engine -B /home/ev3ryy/src/ior_engine/build \
  -DIOR_GAME_LIBRARY=/home/ev3ryy/src/game3/build/game3.so
cmake --build /home/ev3ryy/src/ior_engine/build --parallel
ctest --test-dir /home/ev3ryy/src/ior_engine/build --output-on-failure
```

Интеграционный тест выполняет 64 reload, проверяет движение ровно одной
системой, постоянство числа живых сущностей и ID компонентов движка,
сохранность сущности движка, отказы ABI/экспорта/частичного импорта,
автоматическую перезагрузку, обрезанный файл, восстановление после ошибки,
запрет выгрузки с другого потока/readonly мира и второй независимый мир.
В Linux проверяет `/proc/self/maps`, чтобы выявлять образы, оставшиеся после
`dlclose`. Проверяется также обычный `world.progress()` после выгрузки.
Отдельная тестовая библиотека проверяет порядок и число вызовов `init/update/quit`,
передачу `delta_time`, cleanup после ошибки и вызов `quit` из деструктора загрузчика.
